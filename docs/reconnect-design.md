# ito 切断・再接続 設計

ft_transcendence subject「Gaming and user experience」内 Remote players モジュール要件
（ネットワーク遅延・切断への対応、再接続ロジック）を満たすための設計メモ。

現状の課題（[ito.gateway.ts](backend/src/ito/ito.gateway.ts) / [room.service.ts](backend/src/ito/service/room.service.ts)）:
- 切断 = 即座にプレイヤーを`room.players`から完全削除。猶予なし。
- プレイヤー識別が`socketId`のみで、再接続しても別人扱いになる。
- ゲーム開始後に再接続すると「ゲームはすでに開始されています」で弾かれ復帰不可。
- `turnOrder`に削除済みプレイヤーのsocketIdが残り得るため、ゲームがフリーズしうる。

---

## 1. プレイヤー識別方法

status: 実装済み（ログイン機能導入により移行完了。[login-requirements.md](docs/login-requirements.md)セクション6参照）

- ログイン機能が実装され、ito機能全体がログイン必須になった。`playerId`はDBの`userId`をそのまま使う方式に移行済み（[page.tsx:53-55](frontend/src/app/ito/room/[roomCode]/page.tsx#L53-L55)の`playerId = String(userObj.id)`）
- サーバー/ゲームロジック側は元々`playerId`を「ゲストUUIDかDB userIdか」を意識しない、ただの不透明な文字列として扱う設計だったため、この移行にあたってバックエンド側の変更は不要だった
- ルーム画面は未ログイン（`ft_token`/`ft_user`が無い）だとトップへリダイレクトされるため、ゲストとしてのプレイは不可（[page.tsx:48-51](frontend/src/app/ito/room/[roomCode]/page.tsx#L48-L51)）
- 解消済み: 「別デバイス/別ブラウザからの復帰」も、同じアカウントでログインすればuserId一致により復帰可能になった
- `sessionStorage`（`ito_room_session`）は引き続き「どの部屋にいたか」の記録用途で使用（identity自体はuserIdが担うため、こちらは補助的な位置づけに変わった）

## 2. 切断検知後の対応（ポーズメニュー方式）

status: 実装済み（簡略版。下記の既知の制約を参照）

タイマーによる自動判定ではなく、**部屋のホストが手動で対応を選ぶ**方式にする。

- 誰か（ホストでも一般プレイヤーでも）が切断したら、ゲーム進行を一旦停止し、**部屋のホストにポーズメニューを表示**する
- ホストが選べる選択肢は次の3つ:
  1. 再接続を待つ
  2. 除外して続行（→ section 4のカード除外ルールに従う）
  3. ゲームを中断して終了
- ポーズメニュー表示中、**ホスト以外の一般プレイヤーには「ホストが対応中です」という待機表示のみ**を出す
- **部屋のホスト本人が切断した場合**: 部屋に2番目に入室したプレイヤーへ自動的にホスト権限が移行し、そのプレイヤーがポーズメニューの判断を行う。**元ホストが後で再接続しても、ホスト権限は新ホストが持ち続ける**（自動で元に戻さない）

### 実装メモ（簡略化した点）

- 「1. 再接続を待つ」は専用ボタンを設けず、ホストが「除外して続行」「中断して終了」のどちらも押さない状態＝待っている、として扱う（`ItoRoom.paused`/`pausedPlayerId`、`ito:gamePaused`/`ito:gameResumed`イベント）
- 「2. 除外して続行」は section 4のルールどおり、カード配置前後で除外範囲を分岐させている（配置前: プレイヤーとカードを丸ごと除外／配置後: `ItoPlayer.excluded`フラグを立ててプレイヤーとしてのみ除外し、カードは場に残す）
- ロビー（`WAITING`フェーズ）中の切断はポーズ対象外とし、従来どおり即座に退室扱いにする（保護すべきゲーム進行がまだ無いため）
- 再接続時は`ito:rejoin`＋`RESYNC_STATE`（section 3）により、自分の手札番号・お題・チャット履歴・盤面・フェーズ・ターン順を含めて復元される

## 3. 再接続時の状態復元範囲

status: 実装済み

現状の`ROOM_STATE`（[broadcast.service.ts:50-77](backend/src/ito/service/broadcast.service.ts#L50-L77)）には`theme`・`turnOrder`全体・チャット履歴・各プレイヤーの数字カードが含まれていない。これらを補うため、再接続専用の仕組みを新設する。

### サーバー側

1. `ItoRoom`（[types.ts:14-26](backend/src/ito/types.ts#L14-L26)）に`messages: ChatMessage[]`を追加し、`sendChat`（[game.service.ts:165](backend/src/ito/service/game.service.ts#L165)）でbroadcastと同時にこの配列へpushして永続化する。
2. 新規`RESYNC_STATE`イベントを追加。既存`RoomStatePayload`のスーパーセットとして次のフィールドを持つ:
   ```ts
   interface ResyncStatePayload extends RoomStatePayload {
     theme: string;
     totalRounds: number;
     currentRound: number;
     turnOrder: string[];
     messages: ChatMessage[];
     myCardNumber?: number; // 本人のみに送る
   }
   ```
   `ROOM_STATE`（全員向けbroadcast）はそのまま維持し、`RESYNC_STATE`は**再接続した本人にのみ`emitToSocket`で個別送信**する（`myCardNumber`が他プレイヤーに漏れないよう、既存の`DEALT_CARD`と同じ個別配信パターンを踏襲）。
3. 新規`ito:rejoin`イベント（クライアント→サーバー）。`{ roomCode, playerId }`を受け取り:
   - `room.players`内で該当`playerId`の`socketId`を新しいソケットIDに差し替え
   - Socket.ioのroomに新ソケットをjoin
   - そのソケットにだけ`RESYNC_STATE`を送信
   - 他プレイヤーには「〇〇が再接続しました」通知＋通常の`ROOM_STATE`を再broadcast

### クライアント側

- 接続時、`sessionStorage`に`{roomCode, playerId}`があれば`ito:createRoom`/`ito:joinRoom`ではなく`ito:rejoin`を送る
- `RESYNC_STATE`受信時、この1つのペイロードで画面全体（フェーズ・ターン・盤面・自分のカード・チャット）を丸ごと再構築する

### ポーズメニューとの連携

section 2の「再接続を待つ」を選んでいる間に切断者が`ito:rejoin`してきても、**ポーズは自動解除しない**。ホストが明示的に「再開」ボタンを押すまでゲームは停止したままとする。

## 4. ホストが「除外して続行」を選んだ場合の処理

status: 実装済み

itoは2〜6人の幅を持つゲームで、1人減っても2人以上いれば成立するため、部屋のホストがポーズメニュー（section 2）で「除外して続行」を選んだ場合の実処理を以下のように定める。

### 除外ルール（プレイヤー本人 vs カード）

分岐点は「そのプレイヤーのカードが場（board）に配置され、他プレイヤーに公開済みかどうか」の一点のみ。

- **カード配置前**（DEALING〜INPUT_GENERATING、またはSPEAKINGで自分の手番が来る前）に猶予期間を超えて切断 → **プレイヤーとカード（数字）を丸ごとラウンドから除外**。まだ誰にも見えていないため、除外しても他プレイヤーの推理や画面状態に矛盾は生じない。
- **カード配置後**（SPEAKINGで自分のカードを場に置いた後、ORDERING/REVEAL/ROUND_RESULT）に切断 → **カードは場に残したまま、プレイヤーとしてのみ除外**。既に他プレイヤーが見て判断材料にしているカードを勝手に消すと、推理や並び替え作業が崩れるため。

### その他の影響

- ラウンドホスト（ORDERING操作権限保持者。部屋のホストとは別の役割、turnOrder先頭のプレイヤー）が除外された場合は、`turnOrder`上の次のプレイヤーへ権限を自動委譲する。
- `turnOrder`から除外プレイヤーのsocketId/playerIdを取り除き、現在のターンが除外プレイヤーを指していた場合は次のプレイヤーへ進める（現状のバグ: 除外後もturnOrderに残り得るため、ここを修正する）。
- 残り人数が1人以下になった場合はラウンド/ゲームを続行不可とし、中断扱いにする（詳細な画面遷移は別途検討）。

### 実装メモ

- 「配置後」除外は`room.players`から削除せず、新設の`ItoPlayer.excluded`フラグで非アクティブ化する。`confirmOrder`の正解判定（`correctOrder`）や結果画面はどちらも`room.players`からカード番号・名前・画像を参照するため、削除すると除外プレイヤーのカードの情報が失われてしまうため。
- 「配置前」除外は`turnOrder`からも取り除くが、「配置後」除外は`turnOrder`をそのまま維持する（既にこの人の番は終わっているため、`boardOrder.length >= turnOrder.length`で判定しているフェーズ完了条件の分母がずれないようにするため）。
- フロントエンドには`excluded`フラグを伝搬しているが、除外済みプレイヤーを見た目上グレーアウトする等のUI対応はまだ行っていない（スコープ外、必要になれば別タスク）。

## 決定事項（確定した内容をここに追記していく）

- playerIdは当面クライアント生成のゲストUUID（`sessionStorage`保存。タブ単位で独立させ、同一ブラウザの複数タブが同一playerIdになる衝突を回避する）。将来ログイン機能導入時にDB userIdへ移行できるよう、ゲームロジック側はplayerIdを不透明な文字列として扱う。
- 切断時はタイマーではなく、**部屋のホストがポーズメニューで対応を選択**する（再接続を待つ／除外して続行／中断して終了）。一般プレイヤーには待機表示のみ。
- 部屋のホスト本人が切断した場合、2番目に入室したプレイヤーが新ホストになる。元ホストが復帰しても権限は戻さず、新ホストが持ち続ける。
- 「除外して続行」時の除外範囲は「カードが場に配置済みかどうか」で分岐: 配置前ならプレイヤー+カードごと除外、配置後はカードを残しプレイヤーのみ除外。
- ラウンドホスト（turnOrder先頭、部屋のホストとは別役割）が除外された場合はturnOrder上の次のプレイヤーへ権限を自動委譲する。
- 残り人数が1人以下になったらラウンド/ゲームを中断扱いにする。
- 再接続時は新規`ito:rejoin`イベント＋`RESYNC_STATE`（個別送信）で、フェーズ・ターン順・盤面・自分の数字カード・チャット履歴を丸ごと復元する。チャットは`ItoRoom.messages`として新たに永続化する。
- 「再接続を待つ」中に本人が再接続しても自動でポーズは解除せず、ホストが明示的に「再開」を押すまで停止したままにする。

### 2026-07-31 の改訂（多重切断対応）

当初の「切断者は常に1人」という暗黙の前提を外し、状態モデルを作り直した。
詳細は [docs/disconnect-playerid-architecture.md](disconnect-playerid-architecture.md)。

- プレイヤーの参加状態を`connected`/`excluded`の2ブールから、単一の`status`（`ACTIVE`/`DISCONNECTED`/`EXCLUDED`）へ集約。
  identityは`playerId`に一本化し、`socketId`は「今紐づいている接続」を表すだけの値（切断中は`null`）に降格した。
- `ItoRoom.pausedPlayerId`（単一値）を廃止。切断者一覧は`players[].status`から導出するため、**同時に何人切断しても取りこぼさない**。
- ホストは切断者**1人ずつ**に「復帰を待つ」（`ito:awaitReturn`）か「除外して続行」（`ito:excludePlayer {playerId}`）を選ぶ。
- **切断者が1人でも残っている間はポーズを解除できない**。除外は常に選べるため詰まない。
- 除外対象は`DISCONNECTED`の人に限る（再接続済みの人を誤って除外できない）。
- 除外済みプレイヤーの`rejoin`は拒否して離脱画面へ送る。ホストが未対応/「復帰を待つ」を選んだ切断者はいつでも復帰できる。
- 除外済みプレイヤーは**ラウンド境界（`nextRound`/`startGame`冒頭）で`room.players`から削除**する。
  ラウンド途中に消すと場のカード情報が失われるため、そこまでは`EXCLUDED`のまま席に残す。
- `ito:leaveRoom`は`WAITING`フェーズ専用にした。進行中の離脱は「切断→ホストが除外」に一本化。

### 2026-09-02 の改訂（復帰判定のサーバ一元化と部屋の廃棄猶予）

**1. 「復帰か新規参加か」の判定をサーバに寄せた**

クライアントは`sessionStorage`の記録で`ito:rejoin`と`ito:joinRoom`を出し分けていたが、
記録はタブ単位なので**同じタブでのリロードでしか残らない**。タブを閉じて開き直す・別タブ・
招待リンク経由のいずれも`joinRoom`に落ち、`joinRoom`は進行中の部屋を必ず弾くため
「リロード以外では復帰できない」状態になっていた。

- ルームページは部屋コードが分かる限り**常に`ito:rejoin`を送る**（`/new`での作成時のみ例外）。
  `playerName`を必ず添える
- サーバは席の有無とフェーズで判断する: 席あり＋`EXCLUDED`→離脱画面／席あり→復帰／
  席なし＋`WAITING`→`joinRoom`にフォールバック／席なし＋進行中→拒否
- `sessionStorage`の`ito_room_session`は廃止

**2. 接続中0人の部屋に廃棄の猶予を設けた**

従来は接続中が0人になった瞬間に部屋を削除していたため、2人プレイで相手の切断を待っている
ホストがリロードすると、その一瞬で部屋ごと消えて双方が復帰不能になっていた
（ロビーでも、1人きりのホストのリロードでルームコードと招待リンクが死んだ）。

- 接続中0人でも即削除せず、`ROOM_DISPOSE_GRACE_MS`（2分）の廃棄予約に切り替える。
  猶予内に誰か1人でも繋がれば予約は取り消される（`RoomStore.linkSocket`が取り消し口）
- **明示的な退室・解散・中断は従来どおり即削除**。猶予は「事故で全員落ちた」場合だけの救済
- 切断への対応をタイマーで自動判定しない（section 2）という方針とは衝突しない。
  こちらは進行の判断ではなく、判断する人間が誰も居なくなった部屋のGCに過ぎない
- 接続中0人になった時点ではホスト権を移譲しない。移譲先も切断中の誰かにしかならず、
  その人が戻らなければ誰もポーズを解けない部屋になるため。代わりに**最初に戻った人が
  ホストを引き継ぐ**（`rejoin`。元ホストが後から戻ってもホスト権は返さない）

**3. ラウンド結果を復元範囲に加えた**

section 3 の復元範囲は`ROOM_STATE`に足りないものを補う形で決めたが、`CARDS_REVEALED`が
抜けていた。これは公開の瞬間に一度しか飛ばないイベントなので、`ROUND_RESULT`/`GAME_OVER`中に
復帰した人には成功/失敗も並び順も届かず、結果画面が空欄のままになっていた。

- `ItoRoom.lastReveal`に直近ラウンドの`CardsRevealedPayload`を保存し、`RESYNC_STATE`に同梱する
- `nextRound`でクリアする。`purgeExcluded`の直後なので、残すと既に`room.players`から
  消えたプレイヤーを指したまま復帰者へ送られてしまう
- `GAME_OVER`では残したままにする。最終ラウンドの結果を表示し続ける画面のため

**4. 席を奪われた旧接続を部屋から切り離すようにした**

`rejoin`は席のsocketIdを差し替えるだけで、旧ソケットは socket.io のルームに残ったままだった。
旧ソケットがまだ生きている場合（別タブ・別端末）、`RoomStore.resolve`が
`player.socketId`との一致を検証するため操作は全て無言で無視される一方、
ブロードキャストは届き続けるので、**画面は生きているのに何をしても効かないタブ**になっていた。

- `rejoin`で旧ソケットに`SESSION_TAKEN_OVER`を送り、socket.ioのルームからも外す
  （`BroadcastService.dropSocket`）。受け取った側は自分で切断して離脱画面を出す
- **サーバから切断はしない**。クライアントのsocket.ioが自動再接続して`rejoin`を送り直し、
  2つのタブが席を奪い合い続けるため。切断の判断は通知を受けた側に委ねる
- **席がACTIVEでもrejoinは拒否しない**。通信が切れてからサーバが切断を検知するまでには
  間があり（ping timeout）、その間の再接続を弾くと「復帰できない」が再発する。
  奪い合いではなく「後から来た接続が正」と決め打つ
